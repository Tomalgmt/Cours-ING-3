OBJECTIF ET LECTURE
Les neuf thèmes suivent l'ordre demandé. Dans chaque thème, les constats sont
classés par criticité décroissante ; l'ordre des thèmes n'est donc pas un ordre
global de gravité. Chaque problème présente le fait observé, la menace et
l'argument justifiant sa criticité. Les contrôles du barème sont référencés en
fin de thème. Les points déjà conformes ne sont pas présentés comme des défauts.

Élevée : possibilité locale directe de prise de contrôle ou protection majeure retirée.
Moyenne : atteinte significative, généralement conditionnée par un accès ou une faille.
Faible : faiblesse secondaire ou prérequis plus importants.
Informative : information de contexte à portée limitée.
Les risques locaux élevés restent prioritaires même dans une VM isolée.
Il n'a été procédé à aucune exploitation pour les démontrer.

Contexte réseau observé : NAT VirtualBox ; SSH redirigé du PC depuis
127.0.0.1:2222 vers 10.0.2.15:22. Aucun accès direct depuis Internet démontré.
Aucun correctif, installation, redémarrage ou changement de configuration n'a
été effectué pour cette révision. Le script de notation et Lynis n'ont pas été
relancés. Seule une simulation APT, sans installation, a servi à l'observation.
Le contenu des secrets et des empreintes de mots de passe n'est pas reproduit.

Le service métier doit rester disponible sur 8080/health. Le script annonce un
plafond de 08/20 si ce service est indisponible. La validation complète après
redémarrage est volontairement placée à la toute fin de ce document.

1. COMPTES ET AUTHENTIFICATION
==============================================================================

1.1. Mot de passe administrateur faible et contrôle de robustesse absent
Criticité : Élevée

Constatation factuelle :
La connexion autorisée de moutsss réussit avec le secret de quatre chiffres fourni, non reproduit. Aucun appel actif à pam_pwquality ou pam_cracklib n'a été trouvé dans /etc/pam.d. Le compte dispose de sudo complet.

Menace associée :
Devinette du secret puis prise du compte et élévation administrative.

Argument de criticité :
Le secret est réellement faible ; le NAT limite les sources pouvant joindre SSH mais n'améliore pas l'authentification. Le test B recherche un module, il ne mesure pas la qualité des secrets existants.


1.2. Compte stagiaire encore utilisable
Criticité : Élevée

Constatation factuelle :
passwd -S stagiaire indique P, avec une durée maximale de 99999 jours ; le compte existe. Il dispose aussi de NOPASSWD: ALL (voir thème 2).

Menace associée :
Compromission d'un compte temporaire puis accès root.

Argument de criticité :
Le cumul avec sudo rend ce compte prioritaire. Son caractère inutilisé n'est pas démontré, mais le barème exige sa suppression ou son verrouillage.


1.3. Verrouillage PAM après échecs non configuré dans les fichiers examinés
Criticité : Moyenne

Constatation factuelle :
Aucune ligne active contenant pam_faillock ou pam_tally2 n'a été trouvée dans /etc/pam.d.

Menace associée :
Répétition des essais de mot de passe sans verrouillage par les mécanismes PAM attendus.

Argument de criticité :
Cette absence facilite les essais lorsqu'un service est joignable ; elle ne prouve pas l'absence de toute limitation externe. Fail2ban n'est pas le mécanisme recherché par le test B.


1.4. Comptes de service avec shell interactif
Criticité : Moyenne

Constatation factuelle :
getent passwd indique /bin/bash pour deploy et sauvegarde.

Menace associée :
Usage interactif de comptes de service après obtention d'un moyen d'authentification.

Argument de criticité :
Le shell augmente les possibilités d'un compte compromis ; il ne prouve pas à lui seul que le compte peut actuellement s'authentifier.


1.5. Expiration des mots de passe non contraignante
Criticité : Faible

Constatation factuelle :
PASS_MAX_DAYS=99999 ; les comptes alice et bob ont également un maximum de 99999 jours.

Menace associée :
Secrets anciens ou compromis pouvant rester valides durablement.

Argument de criticité :
La qualité et la révocation des secrets priment sur la rotation automatique, mais le barème exige un maximum de 90 jours. Le test intitulé alice/bob ne consulte en réalité qu'alice.


Points déjà conformes dans les vérifications : root est le seul compte UID 0 ; aucune entrée de mot de passe vide dans /etc/shadow. Ces contrôles n'impliquent pas que les mots de passe sont robustes.

2. ÉLÉVATION DE PRIVILÈGES
==============================================================================

2.1. Autorisations sudo permettant directement root
Criticité : Élevée

Constatation factuelle :
99-laxiste contient stagiaire NOPASSWD: ALL, bob NOPASSWD: /bin/bash et alice NOPASSWD: /usr/bin/find. Ces autorisations ont été confirmées avec sudo -l lors de l'audit initial ; le fichier est toujours présent.

Menace associée :
Une session de ces comptes permet d'exécuter des commandes root sans nouvelle authentification.

Argument de criticité :
Impact maximal avec un simple accès préalable au compte ; aucune faille logicielle n'est nécessaire. La syntaxe sudoers valide ne rend pas ces autorisations sûres.


2.2. Copie de find avec bit SUID root
Criticité : Élevée

Constatation factuelle :
/usr/local/bin/find-suid appartient à root:root, mode 4755. Son SHA-256 est identique à celui de /usr/bin/find. Le montage ne comporte pas nosuid.

Menace associée :
Exécution d'actions avec les privilèges du propriétaire root par un utilisateur local.

Argument de criticité :
Binaire généraliste inutilement privilégié, donnant un chemin très direct vers des opérations root. Aucun essai d'exploitation n'a été exécuté. Contrôle G, placé ici pour son effet de sécurité.


Point déjà conforme : visudo -c valide la syntaxe des fichiers sudoers. La syntaxe et la pertinence des autorisations sont deux contrôles distincts.

3. ACCÈS DISTANTS
==============================================================================

3.1. Authentification SSH par mot de passe et limites permissives
Criticité : Élevée

Constatation factuelle :
sshd -T : PasswordAuthentication yes, MaxAuthTries 10, LoginGraceTime 300.

Menace associée :
Essais répétés sur le compte administrateur dont le mot de passe est faible.

Argument de criticité :
Risque élevé lié au secret effectivement faible ; l'accès réseau actuel reste limité au PC hôte. Le script attend no, au plus 4 tentatives et au plus 60 secondes ; MaxAuthTries s'applique par connexion.


3.2. Aucune restriction nominative SSH dans la configuration globale
Criticité : Moyenne

Constatation factuelle :
sshd -T ne renvoie aucune directive AllowUsers, AllowGroups, DenyUsers ou DenyGroups.

Menace associée :
Des comptes non destinés à l'administration distante peuvent tenter de se connecter si leurs autres conditions d'accès le permettent.

Argument de criticité :
Une authentification reste nécessaire ; l'absence de liste ne signifie pas que tous les comptes sont utilisables. Le script accepte la présence de l'une de ces directives sans évaluer toute sa pertinence.


3.3. Connexion root autorisée par la configuration SSH
Criticité : Faible

Constatation factuelle :
PermitRootLogin yes ; passwd -S root indique cependant L.

Menace associée :
Accès directement privilégié si un moyen d'authentification root est ou devient utilisable.

Argument de criticité :
Le mot de passe root est verrouillé ; aucune connexion root par mot de passe n'est démontrée. Le script accepte no ou prohibit-password.


3.4. Transfert X11 activé
Criticité : Faible

Constatation factuelle :
X11Forwarding yes dans sshd -T.

Menace associée :
Surface supplémentaire lorsque le transfert d'affichage est employé.

Argument de criticité :
Une session authentifiée et l'usage de cette fonctionnalité sont nécessaires ; l'option seule ne constitue pas une intrusion.


3.5. Bannière SSH trop descriptive
Criticité : Informative

Constatation factuelle :
/etc/issue.net contient : « Bienvenue sur le serveur de production - contact: admin@ecole.local ».

Menace associée :
Divulgation d'éléments de contexte utiles à la reconnaissance.

Argument de criticité :
Impact limité. Le test recherche les chaînes production ou admin@ ; il ne demande pas de bannière juridique.


Point déjà conforme : PermitEmptyPasswords=no.

Argument de criticité :
Chaîne de privilèges concrète documentée, sans exécution d'une charge d'essai. Le barème vérifie le dossier ; le script lui-même doit être pris en compte dans l'analyse réelle.


5.3. Répertoire métier modifiable par tous

10. VÉRIFICATION FINALE — À EFFECTUER UNIQUEMENT À LA FIN DU DURCISSEMENT
==============================================================================

Cette procédure est à exécuter plus tard, une fois les modifications terminées.
Elle n'a PAS été exécutée pour produire ce document.
Les commandes Linux ci-dessous se lancent dans un terminal Bash de la VM.

1) Redémarrer la VM
Avant le redémarrage, conserver un moyen d'accès par la console VirtualBox.
Si SSH a été modifié, valider l'accès par clé avant de compter uniquement dessus.

    sudo reboot

Attendre le retour de la VM, puis rouvrir la console ou la session SSH depuis
PowerShell Windows :

    ssh -p 2222 moutsss@127.0.0.1

2) Préparer un dossier de résultats distinct de l'audit initial

    cd "/home/moutsss/Cours-ING-3/Durcissement Linux"
    verification_dir="verification_finale_$(date +%Y%m%d-%H%M%S)"
    mkdir -- "$verification_dir"
    set -o pipefail

3) Vérifier le service métier après redémarrage

    systemctl is-active nginx
    systemctl is-enabled nginx
    curl -fsS --max-time 5 http://127.0.0.1:8080/health

Résultats attendus : active, enabled et une réponse contenant OK.
Si curl n'est plus installé, utiliser wget s'il est présent :

    wget -qO- --timeout=5 http://127.0.0.1:8080/health

Le script de notation possède aussi un test Bash /dev/tcp indépendant de curl.
Si le service ne répond pas, arrêter la validation et diagnostiquer cette
indisponibilité avant de conclure sur la note.

4) Relancer le script de notation

    sudo bash /home/moutsss/tp/check-debian.sh 2>&1 | tee "$verification_dir/check_debian_final.txt"

Lire les lignes PASS/FAIL et le total affiché, pas seulement le code de retour.
Cette version compte 58 contrôles et calcule le score technique sur 60 ;
elle ne comporte pas 60 contrôles. Le test HTTP métier fait partie des 58.
Le script ne retourne pas nécessairement un code non nul lorsqu'un test échoue.

5) Relancer Lynis

    sudo lynis audit system --no-colors 2>&1 | tee "$verification_dir/audit_lynis_final.txt"

Conserver audit_lynis.txt comme état initial. Comparer les problèmes pertinents
avec ce document, sans chercher uniquement à augmenter l'indice de durcissement.

6) Vérifier la persistance et conclure

Après le reboot, examiner en particulier :
- la disponibilité métier et l'accès SSH attendu ;
- les services actifs et les ports écoutés ;
- les règles du pare-feu et l'activation au démarrage ;
- les valeurs sysctl effectives ;
- les profils AppArmor chargés et nginx en enforce ;
- NoNewPrivileges, les journaux persistants, auditd et l'intégrité.

Les résultats du script sont des indicateurs, pas une preuve complète :
- le test « alice, bob » interroge seulement alice ;
- les tests rpcbind/avahi/NFS vérifient l'activité, pas tous leur état au boot ;
- la persistance sysctl est un contrôle textuel d'une déclaration ASLR=2 ;
- certains tests PAM/sudo lisent du texte, potentiellement commenté ;
- les vérifications APT dépendent de la fraîcheur des index locaux ;
- un outil d'intégrité installé et une base présente ne garantissent pas une
  référence saine ni une surveillance régulière.
Consigner les échecs restants et leur explication avant de déclarer le TP terminé.
